# Ship a batch

The only way to merge PRs in this repo, never `merge-prs.sh <n>` or the `gh` merge command directly. Use it once merging is approved: the owner said to merge, or a standing approval covers the PR (e.g. merge without asking when Codex approves with no revisions).

1. For each branch: rebase on `origin/main` if it is behind, push, and `gh pr create` written with the global `pr-descriptions` skill, plus a note if Codex could not run.
2. Run `.claude/skills/ship-batch/ship-batch.sh <n>...` from anywhere in the repo, PRs in merge order. It works in three phases:
   - **Before the lock**, for each PR in turn: wait for its Codex review with the global `merge-prs` skill's gate (`merge-prs.sh --check --wait-review --request-review`, so a running review is waited out and a head that changed since its review gets one requested), then check its branch with `lib/check.sh --changed <merge-base with origin/main>`, in the branch's local worktree or, when it has none (pushed from a cloud session), in a temporary worktree at the PR head (`git fetch origin pull/<n>/head`, removed on every exit path). Steps that already passed for the same files are skipped, so an already-checked branch costs nothing; a pass on top of a base recorded as passed is recorded for the branch's tree. The first PR that fails its gate or check stops the list: the PRs before it still merge, and the run ends by failing with the PR to rerun from.
   - **Under the lock** (`flock` on `ship-batch.lock` in `$(git rev-parse --git-common-dir)`), only what must be serial on the main checkout: merge the ready PRs with `merge-prs.sh` (gate only, never waiting; retargets and rebases stacked PRs, removes merged clean worktrees and branches), pull `main`, `just restow <package>` for every package stowed here that gained, lost or renamed a file (a pull alone leaves a new unit or script unlinked), `systemctl --user daemon-reload` if a user unit changed, reload Hyprland if `home/hypr` changed, restart the stowed bar if `home/quickshell` changed and the lock is `unlocked`, and `just greeter-sync --install` if the merge changed greeter files and sudo needs no password (otherwise it prints the command). A second ship-batch waits for the lock, naming the holder (pid, start time, PRs), for up to `SHIP_BATCH_LOCK_WAIT` seconds (default 900), then gives up.
   - **After the lock**, check main in the real checkout: a tree recorded as passed with `repos/` is not checked again, one passed in a worktree (no `repos/`, so `lib/check/steps/symlinks.sh` skipped the links into it) runs only `lib/check/steps/symlinks.sh`, a previous main recorded as passed runs `lib/check.sh --changed <previous main>`, anything else (or `CHECK_FULL=1`) runs the full `just check`; the pass is recorded. If another batch moves main during the check, the result is dropped and the check stays owed.

   Pass `--skip-review-gate` before the PR numbers only when the owner waived Codex or named another reviewer (e.g. an Opus review while Codex is at its usage limit): it skips the Codex wait and gate and passes the flag to the merge, while each branch check still runs; say so in the PR.

   With no PR numbers it only does the locked and post-lock steps. Resuming: under the lock it records main's commit in `ship-batch-base` (next to the lock) and deletes it only after every reload, restart and sync succeeded, so a rerun after an interrupted merge or reload prints `resuming from <sha>` and redoes them from there. The check is owed separately in `ship-batch-check-base`, written under the lock (an older debt is kept) and cleared only when main's check passes, so a rerun after a failed or interrupted check (with the PRs not yet merged, or none) checks again from the oldest unchecked main; with nothing new and nothing owed it checks nothing. A recorded commit main no longer descends from reloads everything and falls back to the full check. `tests/run.sh` covers the base selection, the lock, the owed check, which packages get restowed, and a whole batch against stubs (what runs inside and outside the lock, a partial batch, a failed check and its rerun).
3. `ship-batch.sh` ends by running `~/.claude/skills/merge-prs/status.sh`; run it again whenever the owner asks what is left, and report what it lists.
4. Tick the finished items in `review.md` and update its handoff if one exists.

If `just check` fails on `main`, fix it with a small follow-up PR before anything else and tell the owner.
